# Apartment Agent Orchestration Design

## Goal

Automate the coordination loop between ChatGPT, GitHub, Codex, and OLX so that investment instructions are generated centrally, Codex executes them in the logged-in browser, and all outcomes are persisted back to the repository for the next decision cycle.

## Current State

The repository already acts as shared persistent state. `AGENTS.md` instructs Codex to pull before work, read `SEARCH_CRITERIA.md`, state files, rejected deals, and relevant negotiation files, then update listings, deals, negotiation history, reports, and `/state` after meaningful actions.

Codex already sends OLX messages and records seller interactions. ChatGPT can read and write the GitHub repository through the connected GitHub integration.

## Architecture

The system uses GitHub as the single coordination layer between ChatGPT and Codex.

```text
ChatGPT orchestrator
    |
    | writes state/next-action.md
    v
GitHub repository
    |
    | Codex pulls repository
    v
Codex browser agent
    |
    | searches / reads / messages OLX
    v
OLX
    |
    | replies / listing state
    v
Codex browser agent
    |
    | updates negotiations, deals, reports, state
    v
GitHub repository
    |
    | next ChatGPT run reads results
    v
ChatGPT orchestrator
```

GitHub is the only shared state. Neither side should depend on conversation history as the source of truth.

## Scheduling

The orchestration loop should run twice per day, aligned with the existing apartment search cadence:

- 08:00 Europe/Bucharest
- 20:00 Europe/Bucharest

The ChatGPT orchestrator run happens first and prepares the next executable instruction.

Codex must have its own scheduled automation that runs after the orchestrator. A GitHub commit alone is not treated as a wake-up event for Codex.

Recommended Codex schedule:

- 08:10 Europe/Bucharest
- 20:10 Europe/Bucharest

The ten-minute gap allows the orchestrator to inspect current state and commit the next instruction before Codex starts.

## ChatGPT Orchestrator Responsibilities

On each run, ChatGPT must:

1. Read `SEARCH_CRITERIA.md`.
2. Read `reports/latest.md`.
3. Read `deals/active.md`, `deals/negotiated.md`, and `deals/rejected.md`.
4. Read `state/next-action.md` and relevant negotiation files when a seller interaction is active.
5. Decide the highest-value next action.
6. Write a concrete, bounded task into `state/next-action.md`.
7. Never issue instructions that authorize a deposit, reservation, signed agreement, binding acceptance, or financial commitment.
8. Leave viewing approval to the user.
9. Avoid re-opening rejected deals unless there is new material information such as a lower price, relisting, or seller re-engagement.

The orchestrator should prefer one clear objective per run rather than giving Codex a broad ambiguous workload.

## `state/next-action.md` Contract

`state/next-action.md` is the command interface between ChatGPT and Codex.

It must use this structure:

```markdown
# Next Action

STATUS: READY

## Objective
<one concrete objective>

## Instructions
- <specific executable instruction>
- <specific executable instruction>

## Stop Conditions
Set `STATUS: NEEDS_DECISION` if:
- a seller accepts or counters;
- a seller asks for a final offer;
- a seller proposes a viewing;
- new information materially changes expected yield or risk;
- the requested browser action cannot be completed safely.

## Safety Limits
- Do not send money.
- Do not pay a reservation or deposit.
- Do not sign or accept contracts.
- Do not make a binding purchase commitment.
- Do not reveal the user's maximum budget.
- Do not arrange a viewing without explicit user approval.

## Generated By
ChatGPT orchestrator

## Generated At
<ISO-8601 Europe/Bucharest timestamp>
```

### Status values

- `READY`: Codex may execute the task.
- `IN_PROGRESS`: Codex has started execution.
- `NEEDS_DECISION`: Codex encountered a material seller response or decision point and must stop.
- `DONE`: the requested task completed without requiring user intervention.
- `BLOCKED`: Codex could not complete the task due to login, browser, listing removal, tool failure, or another execution blocker.

Codex must never execute a `NEEDS_DECISION`, `DONE`, or `BLOCKED` instruction as if it were new work.

## Codex Responsibilities

At the start of every scheduled run, Codex must:

1. Run `git pull --rebase`.
2. Read `AGENTS.md`.
3. Read `state/next-action.md`.
4. If `STATUS` is not `READY`, do not perform seller-facing actions.
5. If `STATUS` is `READY`, change it to `IN_PROGRESS`, commit/push the state change, and execute only the defined objective.

During execution, Codex must:

- verify individual listing pages before acting;
- preserve exact seller messages;
- calculate investment metrics using all-in cost, not only purchase price;
- keep seller-facing messages in Romanian;
- negotiate incrementally and never reveal the user's maximum budget;
- update the appropriate negotiation file after each material seller exchange;
- update active/rejected/negotiated deal files as appropriate;
- update `reports/latest.md` after meaningful changes.

At completion, Codex must set one of:

- `DONE` when the task completed and no decision is needed;
- `NEEDS_DECISION` when user/ChatGPT judgment is required;
- `BLOCKED` when execution cannot continue.

It must commit and push the final state before ending the run.

## Decision Policy

The automation is for analysis, search, and non-binding negotiation only.

The following remain explicit user decisions:

- arranging an in-person viewing;
- increasing an offer beyond a previously approved strategy when a counter requires judgment;
- paying any reservation fee or deposit;
- accepting a binding offer;
- signing or approving any contract;
- disclosing sensitive personal or financial information.

A seller counteroffer, acceptance, request for final offer, or viewing proposal is therefore a `NEEDS_DECISION` event.

## Investment Policy

Codex and ChatGPT continue to use `SEARCH_CRITERIA.md` as the investment policy source of truth.

The automation should prioritize:

- realistic gross yield based on total acquisition cost;
- ease of renting;
- price per square meter relative to local comparables;
- building age and structural risk;
- renovation and furnishing costs;
- agency commission and VAT when applicable;
- floor, balcony, parking, heating, and tenant appeal;
- mortgage cash flow and downside resilience.

Historical rejected listings and seller messages must be preserved so relistings and price changes can be recognized later.

## Failure Handling

If GitHub state is stale, conflicting, or incomplete, Codex must stop and set `BLOCKED` rather than guessing.

If a listing is removed, Codex records the removal and updates the appropriate deal state.

If OLX login is unavailable, Codex sets `BLOCKED` and records that browser authentication is required.

If a seller sends a message that cannot safely be handled under the existing instructions, Codex records the exact message and sets `NEEDS_DECISION`.

## Observability

`reports/latest.md` remains the human-readable summary.

Each scheduled cycle should leave enough repository evidence to determine:

- what instruction ChatGPT generated;
- when Codex started it;
- what seller-facing action happened;
- what changed in investment analysis;
- why the task ended as `DONE`, `NEEDS_DECISION`, or `BLOCKED`.

No important negotiation state may exist only in the browser.

## Out of Scope

This design does not:

- automatically purchase an apartment;
- automatically book viewings;
- automatically send money or deposits;
- create an event-driven webhook between GitHub and Codex;
- treat GitHub commits as guaranteed Codex triggers.

Codex scheduling is configured separately in Codex, while ChatGPT scheduling is configured through ChatGPT automations.
